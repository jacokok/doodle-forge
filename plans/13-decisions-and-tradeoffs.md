# 13 — Decisions and tradeoffs

## Purpose
Preserve major architectural decisions and rationale so agents do not silently change them.

## Scope
Accepted planning decisions, deferred selections, compatibility boundaries and future supersession. These are design decisions, not claims of implementation.

## Technical approach
Use sequential ADR IDs with status, decision, rationale, alternatives and consequences. Changes add a superseding record and links to affected plans/tests; do not erase old rationale. Record exact tool/provider versions once selected and verified.

## Architecture and responsibilities
Implementers propose changes, update this log and relevant plans, and report effects in progress. Contract changes require TS/Godot compatibility tests; persistence changes require migrations; publication changes require crash/concurrency tests.

## Key design decisions

### ADR-001 — One SvelteKit backend (accepted)
**Decision:** SvelteKit/Svelte 5, Tailwind, adapter-node owns UI and APIs; independent Node worker owns long jobs. **Rationale:** shared TypeScript boundaries and minimal deployment complexity. **Alternative rejected:** Express/Nest/FastAPI backend or jobs inside HTTP requests. **Consequences:** server-only import boundaries, bounded handlers and a separate worker lifecycle are required.

### ADR-002 — Local SQLite and filesystem (accepted)
**Decision:** Drizzle migrations with better-sqlite3; WAL, FK enforcement, short transactions and local filesystem blobs. **Rationale:** offline-friendly, inspectable persistence without service infrastructure. **Alternative:** Postgres/object storage adds operational burden prematurely. **Consequences:** one-host deployment, backup coordination, explicit contention handling; mutable files/art ignored by Git.

### ADR-003 — Small durable workflow engine (accepted)
**Decision:** typed DAG/checkpoints in SQLite with leases and fencing, at-least-once handlers, bounded retries, hash cache and approval gates. **Rationale:** reliability at current scale without n8n/Redis/Celery/Temporal. **Consequence:** implement and test failure semantics ourselves; external paid calls cannot be promised exactly-once. Reassess only after measured scaling/operations problems.

### ADR-004 — Versioned content and approval (accepted)
**Decision:** schema version 1 separate from character version and release UUID; immutable published revisions; frozen manifest-hash approval; regeneration creates new version. **Rationale:** reproducibility and child's creative control. **Alternative rejected:** mutable current-character JSON or approval by character ID alone. **Consequence:** history/storage grow, approval must be repeated after any change.

### ADR-005 — Atomic visibility, not cross-resource transactions (accepted)
**Decision:** validate/stage/rename immutable files before SQLite active release activation; API visibility follows ready release DB references. CAS prevents concurrent release lost updates. **Rationale:** no atomic filesystem+SQLite transaction exists. **Consequence:** orphan reconciliation and failure injection required; offline exporter separately atomically renames a complete bundle. Static serving of all storage is forbidden.

### ADR-006 — API in development, bundle in release (accepted)
**Decision:** Godot repository abstraction with API and local bundle implementations; SQLite plugin optional future only. **Evidence:** [godot-sqlite](https://github.com/2shady4u/godot-sqlite) offers a Godot 4 GDExtension requiring native integration. **Rationale:** avoid platform dependencies, live DB schema coupling and exposure of authoring data. **Consequence:** runtime PNG decode remains necessary for all repositories; plugin compatibility is not yet tested.

### ADR-007 — Godot version and renderer (accepted; Phase 1 verification addendum below)
**Decision:** **Godot 4.7.2-stable**, standard GDScript build, Compatibility renderer, matching export templates. **Evidence:** [official archive](https://godotengine.org/download/archive/) consulted during Phase 0 lists 4.7.2-stable (18 August 2026), while 4.8 is beta. **Rationale:** use stable Godot 4, lightweight 2D pipeline and no C# dependency. **Consequence:** Phase 1 verifies actual binary/template versions and host support; version changes require an ADR update, not a floating latest download. Planning-time web verification is not a successful local Godot test.

### ADR-008 — Reusable 2D fighter and sprite convention (accepted)
**Decision:** CharacterBody2D ground-plane root, separate visual jump elevation, AnimatedSprite2D runtime frames, data-driven timing/combat. 256×256 transparent PNG frames with (128,224) foot anchor are v1 project conventions. **Rationale:** consistent automated pipeline and reusable scene. **Alternatives:** 3D or skeletal rigging adds art/tool complexity. **Consequence:** unusual drawings may need manual correction; dimensions are not engine restrictions. Initial executable ability is light melee; other families are extension designs, not untested placeholders.

### ADR-009 — Zod source plus cross-language validation (accepted)
**Decision:** Zod -> reproducible JSON Schema; Godot validates supported v1 fields/semantics via shared test vectors. **Rationale:** single public contract without embedding JS in game or mandating schema plugin. **Consequence:** parity tests are mandatory; JSON Schema alone cannot guarantee hashes, file layout or cross-reference semantics.

### ADR-010 — Mock before paid AI (accepted)
**Decision:** deterministic mock provider and real Sharp outputs precede provider integrations; capabilities route independently. **Rationale:** testability, budget control and contract-first development. **Deferred:** specific real providers/models until Phase 7 capability/privacy/licensing evaluation. **Consequence:** mock success proves mechanics, not AI quality; user consent is required before external transfer.

### ADR-011 — Phase dependency resolution (accepted)
**Decision:** Phase 4 implements minimal publication/approval services and approved fixture seed, Phase 5 adds UI, Phase 6 connects factory, Phase 8 adds bundle implementation. **Rationale:** dynamic API loading cannot depend on future UI/factory; publishing UI needs actual service. **Consequence:** Phase 5 generation UI is honest about unavailable worker functionality; full upload-to-game proof is Phase 6, not Phase 5.

### ADR-012 — Local trust boundary and privacy (accepted)
**Decision:** loopback default, origin/CSRF protections, private originals, bounded/decoded uploads, metadata-stripped derivatives, no secret/personal-data logging. **Rationale:** children's art deserves minimization even locally. **Consequence:** public/LAN multi-user deployment requires authentication, authorization, retention/consent review and HTTPS as a separate prerequisite. Hashes are integrity checks, not signatures.

### ADR-013 — Existing repository root and toolchain selection (accepted)
**Decision:** use existing `/home/doink/projects/doodle-forge` Git root for the DoodleForge product; do not create nested `doodleforge/.git`. Only Markdown delivered in Phase 0. Node LTS/pnpm/dependency exact versions are selected and pinned after Phase 1 compatibility checks. **Rationale:** preserve existing repository and avoid claiming untested dependency combinations. **Consequence:** no executable development commands exist yet.

### ADR-014 — Verified foundation toolchain (accepted, Phase 1)
**Decision:** pin Node 22.23.3 maintenance LTS, pnpm 10.34.7, TypeScript 6.0.3, Svelte 5.57.2, SvelteKit 3.1.0, Vite 8.3.5, adapter-node 6.0.0, Tailwind 4.3.3, Drizzle ORM 0.45.4 / kit 0.31.11, better-sqlite3 13.0.3 and Zod 4.6.7. All direct dependencies use exact versions and the workspace lockfile. **Rationale:** installed Node 22 satisfies checked engine ranges; global Node 26 is not the LTS pin. Kit 3 requires TypeScript ^6 and uses Vite-plugin configuration, `$app/tsconfig` and `$app/env`; use its actual interfaces rather than legacy Kit 2 scaffolding. **Alternatives:** floating latest or upgrading the machine's global runtime; rejected for reproducibility. **Consequences:** Python/C++ may be required solely for native SQLite build tooling. Internal TS source exports are bundled by Vite/esbuild; better-sqlite3 remains an explicit external native runtime dependency in both apps. Built outputs currently run from the checkout, not standalone deployment directories. Registry-based pnpm invocation was used because the mise GitHub binary download timed out. See docs/setup.md and progress for executed compatibility evidence.

### ADR-015 — Incremental persistence and honest foundation seed (accepted, Phase 1)
**Decision:** baseline migration creates characters, character_versions, abilities and character_abilities plus fundamental FK/JSON/status/version checks. Add assets/original links, contract validation, publication immutability, approvals/releases and durable workflow tables through new migrations in their consuming phases (2/4/5/6); never rewrite the baseline. The deterministic foundation seed creates only one synthetic authoring identity, without artwork, versions, catalog abilities, approval or release. **Rationale:** avoid duplicating not-yet-executable contracts or fabricating approved content to make a foundation look feature-complete. **Consequences:** Phase 1 DB readiness does not establish publication/workflow acceptance. Repository optimistic updates, rollback, FK checks, migration exclusion and real two-connection writer contention are independently testable now. Game fixtures/ability catalog remain contract-owned and approval-gated in the planned phases.

### ADR-016 — Executable v1 contract and fixture implementation (accepted, Phase 2)
**Decision:** Implement the plan 04 v1 DTOs as strict Zod 4 schemas in `packages/contracts`; generate committed draft-2020-12 JSON Schema with Zod's built-in converter and format deterministically. Keep semantic references, animation-sheet dimension rules, safe package paths, PNG dimensions, byte lengths and SHA-256 checks in the package validator. Canonical hashing sorts object keys recursively while preserving array order; release manifest hashes remain hashes of exact UTF-8 bytes as specified in plan 04. Add two small authored synthetic character packages with five required animations each. **Rationale:** one executable TS source of truth with explicit semantic checks that a schema converter cannot express; avoid an incompatible third-party converter. **Alternative rejected:** duplicating schema logic or silently adding persistence constraints before a consuming DB feature exists. No Phase 2 DB migration was required. **Consequences:** consumers must reject unsupported schema versions and validate files in addition to structural JSON; Godot parity remains an acceptance task for Phase 4 and has not been claimed. See `packages/contracts` and Phase 2 evidence in plan 14.

### ADR-017 — Fixture-fed Phase 3 prototype boundary (accepted, incremental)
**Decision:** begin Phase 3 with a reusable generic fighter script and a local Phase 2 manifest loader for core movement/jump/melee assertions. Keep fighter configuration data-driven and combat independent of visual assets. **Rationale:** validate ground-plane/elevation separation and attack timing before expanding arena, enemy AI, waves, or sprite rendering. **Consequence:** this increment is not Phase 3 acceptance: active-wave progression, animation rendering, controls, HUD health binding, and manual visual playtest remain outstanding. No Phase 4/API/release behavior is introduced.

### ADR-018 — Node 26 and ordinary pnpm commands (accepted, user-requested)
**Decision:** supersede ADR-014's Node 22 selection with Node 26.12.1 (latest npm `node` release checked on 2026-10-23), installed through mise and selected by CI. Accept `>=26.12.0 <27` in package engines so the installed 26.12.0 runtime also works without an exact-patch rejection. Keep pnpm 10.34.7 and other dependency pins unchanged. **Rationale:** the user requested the latest Node and removal of version-prefixed everyday commands. **Alternatives:** keeping Node 22 or a floating unbounded latest; rejected in favor of a current, reproducible Node 26 baseline. **Consequences:** native SQLite must be rebuilt for the new Node ABI; ordinary `pnpm` commands work with mise shell integration or a compatible system installation. Future major Node upgrades still require validation; historical Node 22 evidence remains unchanged. See plan 14 for actual executed checks.

### ADR-019 — Verified public reads and exclusive operator reconciliation (accepted, Phase 4)
**Decision:** public content reads resolve only DB-ready releases/references, verify bounded exact bytes before conditional ETag responses, and return non-cacheable 503 for corrupt ready representations without fallback/repair. Expose a read-only package subpath so the studio does not load/bundle the Sharp-dependent publisher. Wire reconciliation to an explicit operator CLI, not automatic studio/worker startup. Publishers register operation markers before checking maintenance; reconciliation claims a singleton maintenance directory before checking publisher registrations. Both refuse overlap; concurrent publishers retain existing CAS behavior. **Rationale:** file presence and matching client validators are not evidence of publication/integrity, and process startup alone cannot guarantee no external publisher is active. **Alternatives rejected:** static storage, silent last-good fallback, unlocked “publishers stopped” flags, serializing all publishers, or expiring markers by time/PID. **Consequences:** process death can leave stale markers; only offline operators after stopping all publishers/reconcilers may remove precise confirmed-stale empty markers. No live lock takeover, destructive GC, automatic startup audit, repair or hosted aggregate resource quotas. Trusted same-root local filesystem/service participation remains required. See docs/phase-4-content-api.md and plan 14 for validation.

### ADR-020 — Pinned API repository and generated-schema consumer (accepted, Phase 4 increment)
**Decision:** add a RefCounted repository result boundary and a development loopback HTTPRequest adapter, pinned to its first validated full release for its lifetime. Map validated IDs/version/hashes to documented routes, never portable package paths. Validate exact manifest hash before parsing and bounded asset length/hash/IHDR before returning bytes. Interpret only the emitted v1 JSON Schema keyword subset directly from the shared generated files, with GDScript semantic checks and shared cross-language vectors. Mirror pinned Zod's Unicode-code-point lengths/text trimming and the separate path helper's UTF-16 length cap. Unknown encountered schema keywords fail closed. **Rationale:** avoid duplicated structural DTO constraints and prove the repository boundary independently of rendering/cache/refresh. **Alternatives rejected:** gameplay HTTP coupling, arbitrary path URLs, a second hand-authored schema, adding a general schema plugin, or silently refreshing an in-progress load. **Consequences:** development checkout schema resources need explicit future export packaging; this is not a general schema engine. Godot's NUL-to-U+FFFD conversion requires conservatively rejecting both in paths (extra client restriction). One bounded request per instance; no aggregate quota claim. Refresh explicitly unsupported until a coordinated catalog-swap increment; decoder/factory/cache and API-fed gameplay remain pending. See docs/phase-4-godot-repository.md and plan 14 for executed evidence.

### ADR-021 — Bounded runtime PNG resources and generic CharacterFactory (accepted, Phase 4 increment)
**Decision:** add a serial, repository-independent resource builder and CharacterFactory using only the existing fighter scene. Revalidate the manifest and admit at most 32 MiB declared encoded bytes and 128 MiB conservative pixel working allowance (16 bytes/pixel across all declared assets) before asset fetching/decoding. Recheck exact bytes/hash/IHDR and bounded single-image PNG containers before native decode; refuse compressed metadata/unknown ancillary chunks and APNG. Convert successful images to RGBA8 textures, row-major atlas regions and manifest-driven SpriteFrames. Spawn only after every resource succeeds, with owned combat data and pinned release metadata. **Rationale:** verified headers/hashes are not decodability, and contract maxima across many assets are not a safe per-load allocation policy. **Alternatives rejected:** external PNG editor imports, per-character scenes, gameplay URLs, unbounded parallel decoding or a premature cache/refresh pipeline. **Consequences:** some valid v1 packages exceed the additional runtime admission/subset policy and fail explicitly; these are not shared-schema changes. The allowance is conservative admission, not measured/global CPU/GPU/resident memory enforcement; multiple factories/fighters need a later aggregate policy. Normal arena selection stays fixture-fed. The real built studio/SQLite/approval/publication-to-Godot test proves both fixtures' headless textures and fighter behavior, not catalog replacement, UI selection, exports or manual acceptance. See docs/phase-4-godot-runtime.md and plan 14.

### ADR-022 — Explicit API arena mode and serialized pinned-match loading (accepted, Phase 4 increment)
**Decision:** preserve default fixture mode and add `--content-api[=loopback-origin]` at the arena composition root. Retain one API repository/factory and owned catalog for the arena lifetime, including all matches/resets/retries. Resolve selection/enemies only from that catalog; create every API fighter through the generic factory. Serialize discovery, selection/reset and wave refills with disabled controls and a programmatic overlap gate; do not queue/supersede requests. Freeze combat during loads. Catalog/player/enemy failures clear the match and show explicit errors with deliberate retries, never fixture fallback. **Rationale:** this proves usable published arena selection without mixing releases or prematurely designing catalog swaps/cache. **Alternatives rejected:** per-reset repository replacement, parallel player/enemy loads, implicit fallback, and deferred selections capable of installing stale completions. **Consequences:** Start is not Refresh, even between matches; new publications require a separate arena/application instance until coordinated replacement exists. Empty catalogs remain pinned. Host lifetime/shutdown cancellation and aggregate memory limits remain separate work. Both prepublished fixtures are selectable and playable; mid-match publication proves revision retention, not active-catalog live-addition acceptance. This supersedes only the fixture-only arena limitations of ADR-020/021, not their repository/resource policies. See docs/phase-4-godot-arena.md and plan 14.

### ADR-023 — Opt-in direct-mapped validated PNG disk cache (accepted, Phase 4 increment)
**Decision:** preserve default fixture/API behavior; enable PNG byte reuse only with explicit `--content-cache` or repository injection. Keep index/manifests online and release-pinned. Use 16 fixed slots under app-owned `user://content-cache/v1`, a hash tag plus at most 16 MiB per slot, bounded pre-allocation reads and manifest-based revalidation on every hit. Install complete same-directory temp entries by rename under a synchronous exclusive directory lock. Corruption is removed and fails the current load; only deliberate retry downloads the same pinned asset. Filesystem/lock failures are explicit, never automatic uncached fallback. **Rationale:** a small runnable cache with deterministic disk/work bounds without introducing an unbounded inventory, mutable persistent catalog, LRU metadata or refresh coordination. **Alternatives rejected:** trusting hash filenames, implicit repair/fallback, manifests/catalogs cached as authority, unbounded directory scanning and premature offline-source design. **Consequences:** direct-mapped collisions can reduce hit rate; only encoded bytes are reused, all resource admission/native decoding remains mandatory. Managed steady disk cap is 256 MiB + 1024 bytes; one temp raises peak to 272 MiB + 1088 bytes (not filesystem overhead or externally injected files). Eviction cannot invalidate in-memory resources. Stale locks require explicit offline inspection/removal, not expiry. Trusted local ordinary files required: Godot cannot provide race-free no-follow/nonblocking opens, hostile filesystem mutation protection or power-loss durability. This refines plan 09's proposed hash-named layout, not the immutable content contract. No refresh/catalog replacement, polling, fallback, bundle/export, live-addition proof or phase expansion. See docs/phase-4-godot-cache.md and plan 14.

### ADR-025 — Best-effort catalog polling at safe boundaries (accepted, Phase 4 increment)
**Decision:** API-mode arenas run a five-second timer outside gameplay physics. A tick attempts the same independent candidate-repository/catalog/player preparation used by manual Refresh only when no load or match is active. Busy ticks are dropped, never queued; polling does not inspect or mutate the currently pinned repository. Poll and manual Refresh share one loading/activation gate, so overlap is rejected. Candidate errors and empty catalogs retain the current repository, release, catalog, selection and player, report the error, and are eligible for retry on a later tick or explicit Refresh. No fallback or revision substitution. The timer is owned by the arena and stops when it leaves the tree.
**Rationale:** the existing integration plan specifies a five-second development poll, while ADR-022/024 require match-pinned snapshots and atomic safe-boundary replacement. Candidate preparation reuses the verified manual-refresh transaction-like boundary without changing match lifetime.
**Alternatives rejected:** mutate repository snapshots, replace during combat/loading, queue deferred candidates across a match, automatically fall back/substitute, or let polling race manual Refresh.
**Consequences:** API-mode arenas may make a catalog request every five seconds while eligible; busy periods defer discovery only by waiting for a future timer tick. Failure retries are fixed-cadence, not exponential backoff. This proves polling/replacement mechanics, not adding a new character to an already discovered catalog. Default fixture mode/cache behavior, Phase 3 deferred acceptance and Phase 5 gate are unchanged. See docs/phase-4-godot-arena.md and plan 14.

### ADR-026 — Prefer experimental Svelte async and remote functions (accepted)
**Decision:** For same-app studio interactions, enable and use Svelte's experimental async support and remote functions wherever applicable for data loading, queries and mutations. Keep remote functions thin and delegate business rules to domain services. Continue using explicit SvelteKit HTTP routes for the stable published-content/public API and interfaces or payloads the experimental functions do not suitably support (including binary/streaming cases).
**Rationale:** use Svelte's integrated async/reactivity and type-safe server boundary instead of ad hoc same-origin fetch/action plumbing, while keeping the published API stable and transport-appropriate.
**Alternatives rejected:** retain load/form actions as the default for all studio data interactions; force remote functions onto public protocols or unsupported payloads.
**Consequences:** experimental APIs may change across pinned framework upgrades; isolate their usage, test serialization/validation/errors/pending UI, and reevaluate compatibility on upgrades. This is implementation guidance, not a claim that remote functions are already enabled or implemented. See plan 06 and docs/setup.md.

**Phase 5 compatibility addendum:** verified the installed Svelte 5.57.2 / Kit 3.1.0 APIs and enabled `compilerOptions.experimental.async` plus `experimental.remoteFunctions` in the Vite-plugin config. Use a library query and metadata commands, with shared-schema validation in `CharacterService` and serializable sanitized domain outcomes. Transport failures remain uncertain results, not proof of rollback. The installed adapter-node 6 no longer reads runtime `ORIGIN` and defaults inferred protocol to HTTPS; configure Kit's build-time `paths.origin` from validated `loadConfig().origin` for local HTTP instead of disabling origin checks or trusting forwarding headers. Builds are origin-specific: set the same `ORIGIN` at build/runtime and rebuild when it changes. The browser harness rebuilds for its test origin using temporary storage; JSON API and public content routes remain explicit and unchanged. See setup and plan 14 for actual compatibility/browser evidence.

### ADR-027 — Authoring archive does not revoke published content (accepted, Phase 5)
**Decision:** metadata CRUD edits only mutable character identities; DELETE archives with an expected edit revision, hides the identity from authoring reads and prevents further edits. It never deletes or rewrites frozen snapshots, approval decisions or ready release membership. The initial slice accepts name/description/body type only; new identities explicitly retain unselected fighting style and no power until creative-choice support exists. Explicit JSON routes implement the planned API; future same-app UI continues to prefer remote functions over the same domain service (ADR-026).
**Rationale:** hiding an authoring identity must not become an implicit publication rollback or loss of history. No executable ability or generated version should be fabricated by metadata CRUD.
**Alternatives rejected:** hard deletion, implicit release revocation, editing frozen metadata, accepting arbitrary executable creative configuration, or treating this API slice as completed UI/factory support.
**Consequences:** archived characters can remain playable in historical/current ready releases. Unpublication/retention requires separately specified deliberate operations. No new migration or workflow is introduced. See docs/phase-5-authoring.md and plan 14.

### ADR-028 — Immutable private originals and revision-checked selection (accepted, Phase 5)
**Decision:** a character may accumulate immutable original/derived-preview pairs; one selected original reference is mutable authoring state. Attaching/replacing requires the same expected edit revision as metadata/archive and increments it atomically with both asset records. Replacement retains previous pairs, never overwrites bytes or edits published/frozen versions. Archive blocks authoring image reads/attachments without deleting art or revoking publication. Retained originals are privately addressable by owning non-archived character plus original ID; no arbitrary storage path API. No versions/jobs/generation are fabricated.
**Rationale:** plans require original preservation/history but did not settle selection/replacement semantics. A single shared CAS token prevents concurrent uploads, metadata edits and archive from losing changes. Explicit Replace original is the deliberate selection action; uploading does not submit unsaved metadata.
**Transport/storage:** ADR-026's binary exception uses explicit multipart upload/private image routes, leaving metadata remote functions/JSON APIs intact. Count streamed bytes before parsing a bounded in-memory multipart envelope (10 MiB + 64 KiB); validate one file at most 10 MiB, magic/MIME and a full strict Sharp decode up to 20 megapixels. Refuse animated/multipage/truncated images and conservatively refuse compressed PNG ancillary metadata to avoid decompression outside pixel limits. Preserve originals; derive oriented metadata-stripped PNG previews within 1024×1024. Files use generated keys, exclusive writes, flush/read-only permissions before short DB adoption; private reads verify confined no-follow regular files, exact bytes/hash and ownership.
**Alternatives rejected:** overwriting a current original, replacing without expected revision, changing metadata implicitly during upload, public/static image storage, unbounded multipart parsing, or prematurely introducing workflow/version semantics.
**Consequences:** additive migration 0003; history consumes storage, failed/crashed adoption may leave private unreferenced files, and no automatic destructive GC/retention is introduced. Adapter-node must receive `BODY_SIZE_LIMIT=10551296` for the intended envelope (default 512K is safer but more restrictive); Sharp stays external as a native production dependency. Local loopback trust remains, not hosted authentication/authorization. Per-request bounds are not aggregate memory/concurrency quotas; no power-cut/other-platform durability claim. See docs/phase-5-uploads.md and plan 14.

### ADR-029 — Conservative creative-choice authoring catalog (accepted, Phase 5)
**Decision:** shared browser-safe contracts own the selectable IDs/labels and strict authoring validation: fighting style `unselected` or `light_melee`; special power `none` only. Light melee names the existing fixture/runtime capability, not a new combat preset or an automatic manifest mapping. No projectile, elemental, healing or other special power is executable in v1, so none is offered as a supported selection. The power control explicitly explains this limitation. Body type reuses the existing input.
**Rationale:** plans 04/ADR-008 and executable v1 attacks/abilities support melee only; the persistence ability tables are schema scaffolding, not a populated executable power catalog. Inventing choices would imply unsupported combat semantics. Creative selections are mutable authoring intent, not version abilities; saving never generates art, freezes versions, enqueues jobs, approves or publishes.
**Compatibility:** create accepts optional choices with `unselected`/`none` defaults, preserving existing metadata clients. PATCH accepts choice-only or mixed edits under the same identity revision CAS as metadata/upload/archive. Omitted choices stay unchanged. Existing fixture/foundation `light_melee` and new `unselected` identities are supported. Unknown legacy stored strings are displayed as unsupported, never normalized on read; the UI omits unchanged choices so metadata edits preserve them, and deliberate replacement must use the supported catalog. No arbitrary configuration or DB ability rows are accepted/created. Existing text columns suffice; no migration or runtime/content-schema change.
**Alternatives rejected:** speculative named styles/powers, free-form configuration, rewriting legacy rows, forcing choice defaults on metadata-only edits, or separate revision tokens. Future expanded catalogs need a new explicit policy and matched executor/contract tests before claiming runtime support. Thin existing remotes/JSON routes continue to dispatch through CharacterService (ADR-026); original and publication boundaries remain ADR-027/028.

### ADR-030 — Keep browser-used manifest schemas Node-free (accepted)
**Decision:** Export the shared character/release schemas and inferred types through `@doodleforge/contracts/manifest`, a module with no Node built-ins. Keep filesystem, path and cryptographic package-validation helpers in the existing root contracts entry; the root re-exports the same manifest schema definitions for existing server/CLI consumers. Browser code that validates frozen manifest DTOs must import the Node-free entry.
**Rationale:** importing the root entry into a Svelte client bundle pulled `node:crypto`, `node:fs/promises` and `node:path` into browser code, causing runtime failure. An explicit subpath preserves one schema source while enforcing the browser/server dependency boundary.
**Alternatives rejected:** duplicate a reduced animation schema in studio code, remove useful server validators from the root API, or polyfill Node modules into the browser.
**Consequences:** shared schema compatibility remains unchanged; package exports expose an explicit browser-safe entry. `pnpm check`, contract tests, production build and browser E2E verify the boundary. See plans 04/06 and plan 14.

### ADR-031 — Bounded Phase 5 fixture review/publication commands (accepted)

**Decision:** User has authorized remaining Phase 5 review/publication mutations before Phase 6. Use shared strict DTOs, hash-bound version identity and expected latest decision order. Decisions append with order/active-owner CAS inside SQLite; publication rechecks both at activation and on the already-active idempotent path. The local reviewer label is server-owned, not authenticated identity. Native confirmation dialogs pin version/hash with Cancel-first focus; stale/uncertain results require explicit review refresh and preserve unsaved authoring input.

**Incremental protocol exception:** Before durable Phase 6 jobs exist, supported small packages use synchronous commands returning actual 200 results (including release ID), never fake 202 jobs. Admission is limited to fixture v1 packages selected by server allowlist or already-ready package paths, exact frozen canonical hash, at most five assets / 2 MB compressed / 2 million declared pixels per package and an admitted catalog of at most eight identities. No client path or source-snapshot path hint is used. Existing publisher performs full native decoding, durable writes and atomic activation. Larger/generated unpublished sources remain unavailable until Phase 6's asynchronous publication jobs; this does not authorize generation in HTTP handlers. Local filesystem stalls remain an operational risk; interrupted/uncertain commands require inspection/reconciliation, not blind retry.

**Private review delivery:** A new no-store, owner-checked frozen-sheet route permits review before publishing only for these supported sources. It verifies bounded bytes/hashes and never exposes originals, source snapshots, paths or unrelated versions. Public game delivery still requires ready-release membership. Archive denies private review/actions but never removes historical ready releases. Rejection/revocation cannot retroactively unpublish.

**Consequences:** No migration or workflow framework added. Source admission is intentionally narrow and must be replaced/extended by persistent generated-package registration and publication jobs in Phase 6. Manual accessibility/observed-child acceptance remains pending; authorization to implement is not evidence of acceptance.

### ADR-032 — Durable Phase 6 foundation before mock execution (accepted)

**Authorization:** The user explicitly defers Phase 5 manual accessibility/screen-reader and observed child-usability acceptance and authorizes Phase 6. This is a phase-gate exception, not evidence those checks passed.

**Decision:** Add migration 0004 only; preserve prior SQL. SQLite owns jobs, immutable typed-input identities, dependency IDs, step selection and attempt history. Workflow owns shared-envelope validation, stage-specific input/output schemas, canonical hashes and handler execution outside transactions. Worker/AI remain composition/provider boundaries; no HTTP generation or production polling is introduced in this increment. Nullable job version supports pre-freeze generation; supplied version IDs must belong to the job character. Enqueue validates the entire acyclic same-job DAG and uses a canonical request/graph identity for idempotency.

**Lease protocol:** Short `BEGIN IMMEDIATE` transactions serialize due/dependency-ready claims, increment persistent attempt/fence numbers, and insert an attempt. Default lease 60 seconds; heartbeat and completion require matching worker, step, attempt ID, fence, running uncancelled job and strictly unexpired lease. Heartbeat cannot shorten a lease. Expiry recovery records an expired attempt and requeues after deterministic exponential backoff, or fails at budget. Cancellation atomically ends running attempts and prevents further claims/adoption; adopted checkpoints remain immutable. Terminal failure is fail-fast for this increment: pending siblings/descendants become blocked and running sibling attempts cancelled. No exactly-once external side-effect promise.

**Bounded increment:** Generic handler execution validates persisted input hashes and schema output, but no asset-producing handler, cache reuse or provider is connected. All-computation completion intentionally leaves the job running until snapshot/gate orchestration is implemented; no waiting-review/success inferred from file existence. Retry budget defaults to three via workflow request validation; basic retry delay is 2/4 seconds before remaining claims, no jitter/Retry-After classifier yet. Worker poll/heartbeat/shutdown loops, gate transitions, provider request bookkeeping, orphan verification, selective regeneration, progress API and durable publication remain next increments. Existing bounded Phase 5 synchronous fixture publication (ADR-031) stays runnable until an explicitly tested replacement; SQLite fences alone do not authorize bypassing the publisher's filesystem/activation protocol.

**Alternatives rejected:** conversation persistence as queue durability, calling generation in routes, enabling a success-only mock, or replacing publication before restart/cancel tests. All clocks are same-host UTC milliseconds with an injected deterministic clock in tests; distributed clocks and power-loss testing are not claimed. Ended attempts and adopted checkpoints have SQL immutability guards; raw maintenance is not an application transition API.

### ADR-033 — Mock-only worker execution before artifact pipeline (accepted, Phase 6)

**Decision:** Compose the durable runner into the existing worker, not a new service/framework. Poll every second with default concurrency one, configurable to 1–4. Heartbeat each active attempt every 15 seconds against a 60-second lease; inspect cancellation/ownership each poll. Claims filter by exact registered stage key/version, so unknown/future stages remain queued without attempt consumption. Recovery processes at most 100 expired leases per poll to bound write-lock work. Local active work is keyed by attempt ID, not step ID, so an old abort-ignoring task cannot remove a reclaimed attempt from concurrency/shutdown tracking. Scheduler persistence faults stop claims and cause the production runtime to shut down with a sanitized failure event.

**Provider boundary:** `packages/ai` defines capability-discriminated requests/results and `deterministic-mock@1`; no SDK, credentials or network. Mock analysis preserves explicit creative choices, and bounded frame requests produce actual transparent nonempty distinguishable PNG candidates via pinned Sharp, with hashes, seed/provider version and zero-cost/synthetic warnings. Only the schema/provenance-validated description-analysis stage is registered with the worker. Frame candidates remain in-memory provider outputs until artifact persistence/verification arrives. These are synthetic mechanical checks, not faithful child-art interpretation, review readiness or the capture-first full pipeline.

**Shutdown/retry:** Stop polls/claims, clear heartbeat timers, abort handlers and fence owned work through transactional relinquishment before closing SQLite. Attempt outcome is cancelled with `WORKER_STOPPED`; retry consumes the existing bounded attempt budget and uses persisted backoff, not user job cancellation. Wait at most five seconds for handlers; executor abort checks prevent late checkpoint writes after SQLite closes. Hard kills use ordinary lease recovery. Only explicit known-safe mock transient failures retry; unknown errors/invalid outputs fail permanently and persist fixed codes rather than raw messages. Real-provider billing ambiguity/Retry-After/jitter is not implemented or silently generalized.

**Consequences:** Health remains generation-unavailable until upload-to-review works; normal startup queues nothing and no Studio enqueue/UI or publication authority changes. Jobs whose computation has finished still await future snapshot/gate orchestration rather than inferred success. Native Sharp is externalized in worker builds as an installed production dependency. No new migration is needed: existing attempt outcomes support relinquishment. Existing bounded synchronous fixture publication remains until the ordered durable publication increment. Same-host clock/event-loop assumptions remain; a nonresponsive handler can retain a slot until it settles, and the runner does not force-close arbitrary external resources.

### ADR-034 — Private attempt-scoped artifacts and pinned original capture (accepted)

**Baseline discrepancy:** The supplied handoff described an ADR-033 mock worker, but the inspected clean checkout has ADR-032 only, an empty AI package and health-only worker. Do not invent the absent implementation or its verification. Reserve 033 for reconciliation with that handoff; use 034 for this independently verified increment.

**Decision:** Keep private PNG artifacts in a separately provisioned root with server-derived UUID step/attempt/artifact paths. References include hash, compressed size, media type and dimensions; no arbitrary storage paths or inline artwork. Store immutable outputs in attempt checkpoint JSON rather than prematurely extending original/preview-only `assets` rows. Future freeze/promotion must register validated sources before publication; artifacts have no public delivery authority.

**Installation and adoption:** Strictly decode bounded bytes, write an exclusive temp file, chmod read-only, fsync, atomically hard-link to a unique final path without replacement, unlink the temp name and fsync directories. This same-filesystem protocol replaces overwrite-capable rename for individual files. Stage definitions declare their produced artifact references; execution verifies current attempt membership and file bytes/hash/dimensions before SQLite's existing final lease/cancellation fence. Old/cancelled attempts may retain private orphans but cannot select them. Consumers reverify on read; automatic cache reuse, deletion and quotas are not introduced.

**Capture:** Resolve only the queued original UUID/hash and immutable owner/kind/key, not the mutable current attachment. Rehash exact bounded original bytes and verify decoded dimensions; use existing strict upload image processing to derive an oriented metadata-stripped preview. Preserve original bytes. The stage is library-only until separately tested worker composition; no generation in routes, provider calls or artwork transfers.

**Limits and tradeoffs:** 10 MiB per PNG, 20 million decoded pixels, maximum edge 4096, at most 100 declared artifacts; read no-follow/nonblocking descriptors and reject symlink roots/ancestors. Local trusted-process filesystem remains the threat model; privileged concurrent tree replacement, aggregate retention, power-loss durability and non-Linux filesystem support are not claimed. Hard-link installation needs same-filesystem support. No new migration, package version, release protocol or phase advancement.

### ADR-035 — Offline mock capabilities and adopted dependency inputs (accepted)
