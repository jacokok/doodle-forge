# Phase 4 — published-API arena selection

The arena now has two explicit launch modes. Default remains the trusted development fixtures, including `--fixture=comet` and the unchanged fixture regression suite. Against an already migrated studio with explicitly approved **and published** content:

```sh
godot --path apps/game -- --content-api=http://127.0.0.1:5173
```

`--content-api` alone uses that same default origin. `--content-api=` is an invalid configuration, **not** fixture mode. API mode takes precedence over `--fixture`. Only the repository's supported loopback HTTP origins work. See [publication](phase-4-publication.md) and [API](phase-4-content-api.md); approval alone does not publish, and the integration seed is test-only, not a production publication command.

## Discovery, selection and match lifetime

`scripts/arena.gd` is the composition root for one `ApiCharacterRepository` and `CharacterFactory`. It owns a selection copy of the first validated full catalog. Option indices resolve only to this snapshot's ID/version pairs. Initial labels show short IDs and versions (the release index has no names); successful loads replace them with validated character names/versions. No hardcoded API fixture names or package URLs drive selection or enemy creation.

Discovery shows a loading message with disabled controls and no fixture player. Selection loads a fresh generic player, binds health, clears any prior enemies/completion state and returns to practice. Start/restart resets the player and starts the existing two capped waves. Enemies use the next catalog entry, wrapping for a one-entry catalog. Player input and AI are paused during resource loading. All fighters are created through the existing factory; combat timing, scenes and fighter/AI scripts are unchanged.

One arena instance retains **one repository and release** through practice, each active match, resets and explicit retry. API mode polls every five seconds; each timer tick is a best-effort refresh attempt only when `_loading` and `running` are both false (idle practice, loss, or completed match). Ticks during loading or active combat are dropped, not queued, and never alter the pinned repository/catalog. Polling stops with the arena node. API mode also has a deliberate Refresh control; Start, reset, retry and HTTP/cache errors never refresh implicitly. Manual Refresh is permitted at the same safe boundaries. Calls during loading or active combat are rejected without queueing. Poll and manual Refresh use one operation gate; a manual request during a poll (or vice versa) is rejected.

Refresh constructs a separate candidate repository/factory, validates its complete catalog, and builds the currently selected character before activation. Selection is reconciled by character ID; if absent, the first candidate entry is used. Only after successful resource admission, fetch, integrity checks and native PNG decoding does one synchronous boundary install repository/factory/catalog/release/player and free the prior player. Until then old catalog and fighter remain coherent. Empty catalogs and any candidate/catalog/resource failure retain that old state and show `Refresh failed: <code> · previous catalog retained`; a deliberate later Refresh retries. If no prior catalog exists, failure remains an initial error with no fixture fallback. No old/new release mixing occurs inside a match. Poll and manual Refresh share the candidate preparation and activation path. Failed/empty polling retains the previous coherent state and reports the explicit error; it does not substitute a revision or disable the cache. A later timer tick or deliberate manual Refresh can retry. There is no pending-candidate queue: publication during a match is observed only on a later eligible five-second tick.

## Loading and failure policy (ADR-022)

Only one arena load operation can run. Both UI controls are disabled during it; direct selection/start/wave calls also reject overlap, without queuing or superseding the operation. Thus no older completion can overwrite a newer accepted selection or reset. Wave refills use the same gate and factory, outside combat work. The arena/HTTP host must remain alive across awaits; shutdown cancellation is still separate work.

Catalog, player or enemy load failure stops the match, removes all its fighters, zeros health and shows `Content error: <code>`. There is no partial playable match or silent fixture substitution. After catalog failure, selection stays disabled and Start retries discovery. After player/enemy failure, selection and Start are enabled: choose another pinned entry or explicitly retry the selected match. A successful discovery retry prepares the first character; press Start again to fight. An empty validated catalog reports `empty_catalog`; because that snapshot is pinned, retry does not refresh it. Restart the application after publishing content.

## Executed integration coverage

`mise exec -- node tools/godot-validation/run.mjs --published-api` (also invoked by `mise exec -- pnpm test:godot:api`) builds studio/worker and uses migrated isolated SQLite with real approvals/publications, not a content proxy. The harness first publishes only Sprout, then `tests/published_addition.gd` discovers that one-entry catalog, publishes Comet through the real publisher while the arena remains alive, invokes the existing polling candidate path, and selects/plays Comet. The same run then retains the published-factory and full arena regressions against the two-character catalog. A test-only loopback control server coordinates publication and temporary corruption/restoration of ready files; it is never a production route or content source.

The live-addition suite verifies the arena initially sees only Sprout; Comet is not published until after discovery. Before candidate activation the old one-entry catalog/release remains installed. Polling then discovers the new release and membership; Comet becomes selectable, loads real published textures into the same generic fighter scene, moves, starts an arena match against Sprout, and damages it using its data-driven combat definition. The harness fingerprints project/gameplay scripts and scenes before publication and proves those fingerprints unchanged afterward. This establishes catalog membership addition, distinct from publishing a new revision of an already-listed character.

The existing arena suite also verifies discovery/loading controls, five-second poll cadence, polling/manual-refresh rejection during loading and active combat, failed-poll retention, both selections and distinct runtime textures, generic factory metadata, HUD, input movement/jump, timed/deduplicated melee, overlapping actions, capped waves/completion/loss, reset pinning after real publication, candidate replacement/selection reconciliation, failed-refresh retention, new-instance revision discovery, catalog/player/enemy corruption failures, no partial match/fallback and explicit retries.

Add `--content-cache` to explicitly enable the [bounded PNG disk cache](phase-4-godot-cache.md); without it, the original API behavior and corruption/retry regression remain unchanged. The flag is ignored in fixture mode. Cached bytes do not change release/catalog lifetime or bypass resource validation.

The data-only live-addition acceptance is covered by the separate one-character-then-addition harness described above; the preexisting two-fixture/revision-retention assertions remain regression coverage, not the addition proof. No offline bundle or export packaging is claimed. Phase 5 remains unauthorized. Phase 3 manual graphical/active-AI acceptance remains deferred, not passed. Resource admission remains per load, not a global resident-memory guarantee.
